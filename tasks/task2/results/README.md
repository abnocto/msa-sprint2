# Задание 2: booking-service и booking-history-service

## To Be

Создание брони:

1. Пользователь вызывает `POST /api/bookings` монолита, монолит проксирует запрос в `booking-service` (gRPC).
2. `booking-service` проверяет пользователя, отель и промокод по REST монолита через ACL. Логика перенесена из монолита без изменений.
3. `booking-service` сохраняет бронь в свою БД `booking-db`. Ид брони генерируется так, чтобы не пересекаться с ид из монолита (используется Snowflake, привязанный к дате), это важно для миграции данных из старой базы.
4. `booking-service` публикует событие `BookingCreated` (вся бронь) в Kafka, топик `booking-created` (топик создает контейнер `kafka-init` еще до старта сервисов).
5. `booking-history-service` читает событие и сохраняет сырую бронь в `booking-history-db`. Статистика по пользователям, отелям, дням получается запросом (`GROUP BY`), без нагрузки на боевую БД. Повторное событие не создает дубль (естественная идемпотентность по ид брони - первичному ключу).

Список броней:

1. Запрос `GET /api/bookings?userId=` к монолиту.
2. Монолит проксирует запрос в `booking-service` (gRPC), тот читает брони из своей `booking-db`.

## Стратегия миграции данных

1. Копируем старые брони из БД монолита в `booking-db` с исходными идентификаторами.
2. Включаем прокси в монолите (`BOOKING_SERVICE_EXTERNAL_HOST/PORT`): `POST` и `GET` идут в booking-service.
3. Повторяем копирование из шага 1 (нужно, чтобы получить брони, созданные в монолите между шагами 1 и 2).

Перенос данных встроен в `regress.sh` перед тестами, поэтому тесты проверяют и миграцию.

## Намеренные упрощения решения

- Откат на монолит: для возможности отката с микросервиса монолит должен знать о новых бронях. Нужен временный консьюмер `BookingCreated` в монолите, который пишет брони в старую таблицу. Здесь он не реализован для упрощения (чтобы не трогать монолит, который поставляется готовым jar), поэтому брони из booking-service в БД монолита не попадают. При откате их нужно перенести обратно тем же копированием в обратную сторону.
- Событие в Kafka отправляется после сохранения брони, без Transactional Outbox (тоже для упрощения). При сбое Kafka бронь не попадет в историю.
- Между включением прокси и повторным копированием (шаги 2-3 стратегии миграции) новые брони монолита не видны в списке.
